# U6.4：Git 安全固化——审核与提交计划

> **阶段性质：先审阅计划，不执行 Git 写操作。**
>
> 当前任务只负责核实工作区、审查 U6.3 已生成的固化建议，并输出逐文件、可人工审核的提交计划。收到用户明确批准前，禁止 `git add`、`git commit` 或任何会改变 Git 索引、分支、工作区历史的操作。

## 1. 背景与目标

U6.3 已通过默认运行行为核验：日常启动实际加载 V2.1（136 类），四类 bully 候选与 `collie-pair` 双候选均按当前配置工作；后端 265 项测试、前端 85 项测试和前端构建通过。V1.1/V2.1 权重、数据目录、正式 SQLite 与 `uploads/` 的保护快照一致。

当前 Git 尚未固化。U6.3 报告记录的基线为：

- HEAD：`547c55d v2训练前`
- 已跟踪修改：18 项
- 未跟踪项：83 项
- 合计：101 项
- 其中 10 个文件包含多个阶段的混合改动，不能声称可以按任务名称直接干净切分。
- U6.3 已提供 `reports/u6_3_default_runtime_and_freeze/recommended_commit_plan.md` 和 `git_change_inventory.csv`，本任务应在其基础上核验，不应另起炉灶或静默改写历史记录。

**本阶段目标：**

1. 再次确认当前工作区状态与 U6.3 基线是否一致；若有变化，列出变化，不覆盖已有证据。
2. 逐文件审阅差异，判定运行时必需代码、对应测试、启动脚本、训练基础设施、诊断/验收脚本、实验产物和来源不明的改动。
3. 为每个拟提交组生成精确文件名单、依赖关系、提交说明草案及可复制的 PowerShell 命令。
4. 明确哪些文件暂不提交，以及混合改动带来的风险。
5. 交付审核报告后停止，等待人工批准；不得在本任务中执行提交。

## 2. 不可违反的保护要求

### 2.1 Git 操作限制

本轮允许只读命令，例如：

- `git status --short`
- `git rev-parse HEAD`
- `git diff --stat`、`git diff --name-status`、`git diff -- <path>`
- `git diff --cached --stat`、`git diff --cached --name-status`
- `git ls-files --others --exclude-standard`
- `git log -n ... --oneline`

本轮禁止执行：

- `git add`、`git commit`、`git commit --amend`
- `git reset`、`git checkout`、`git restore`、`git switch`
- `git clean`、`git stash`、`git cherry-pick`、`git rebase`
- 任何会更改索引、HEAD、分支、提交历史或丢弃工作区更改的操作

可以在**报告文本**中列出未来建议使用的 `git add` / `git commit` 命令，但不得运行这些命令。不要为了获得“干净状态”去回退、删文件或移动文件。

### 2.2 模型与数据保护

不得训练或评估模型，不得访问 test split，不得修改/删除/移动任何训练、验证或测试图片、标签、数据划分、checkpoint 或模型元数据。不得修改正式 `data/app.db`、项目 `uploads/`、默认模型路径、候选组阈值、候选开关或启动配置。

不得删除 U6.3 的隔离 runtime 目录，也不得清理 `.cache/`、`artifacts/`、`reports/` 或其他未跟踪项。实验权重与报告默认不加入 Git，除非用户之后单独批准。

## 3. 执行步骤

### A. 先捕获只读基线

1. 记录当前 HEAD、分支名、`git status --short`、未暂存差异统计、已暂存差异统计和未跟踪文件清单。
2. 将结果与 U6.3 的 `git_status_before.txt`、`git_diff_stat_before.txt`、`git_diff_name_only_before.txt`、`git_change_inventory.csv` 对照。
3. 报告当前状态是否仍为 18 个已跟踪修改、83 个未跟踪项。如果数量不同，按具体路径列出新增、消失、状态变化，不要假设是错误，也不要自动处理。
4. 先记录状态，再创建本轮输出目录，防止本轮报告自身影响对原始工作区项目数量的比较。输出目录：`reports/u6_4_git_freeze_review/`。

### B. 审阅每个候选文件的差异

1. 对所有已跟踪修改文件，逐一阅读完整 diff；不能只依赖文件名、任务标题或之前报告的分类。
2. 对关键未跟踪源文件，阅读内容并检查是否依赖被忽略的 checkpoint、临时目录或机器本地绝对路径。
3. 对测试文件，确认它对应的实现与断言；对脚本，确认是后续必要的项目工具还是一次性的验收脚本。
4. 对 `artifacts/`、`reports/`、`data/`、`uploads/`、`.cache/`、隔离 runtime 和 checkpoint，默认列为不提交项，并在报告中给出理由。不得仅因路径位于 `reports/` 就声称其内容无价值；应说明项目历史中 `reports/` 一直未跟踪，建议延续既有惯例。
5. 不要把“文件属于某任务”当作足够证据；对无法明确归属或混合改动的文件标记风险，并说明整文件提交的影响。

### C. 建议的固化分组（需要逐文件复核，不可机械套用）

依据 U6.3 的现有建议，先评估以下组别及依赖关系：

- **A. 正式运行代码**：V2.1 默认模型接入、136 类中文名称、预测服务与两套候选组所需的运行时模块。
- **B. 配套测试**：与 A 组运行时实现相对应的后端和前端测试。
- **C. 启动入口**：相关 `.bat` 文件中确实属于本次接入的更改。
- **D. 训练基础设施（独立审核）**：`ml/train.py`、`ml/dataset.py`、`ml/u6_pair_training.py`、`tests/test_train_extensions.py` 等。此组不应混入生产功能提交；需清楚记录 U4、U6-C 和 warm-start 修复等来源。
- **E. 任务单/必要开发文档**：只有确有长期维护价值、且用户决定入库时才建议提交。
- **F. 暂不提交**：报告、截图、CSV、隔离 runtime、模型权重/实验产物、临时缓存以及尚未证明为长期维护工具的脚本。

这只是审阅框架，不是预先批准的文件清单。最终报告必须提供每组的**完整相对路径列表**，并标明依赖、混合改动风险、建议提交顺序与不提交原因。

### E. 测试核验

本任务不修改源代码，因此可引用 U6.3 的近期测试结果作为基线：后端 265 passed、前端 85 passed/12 files、`npm run build` 成功。若为确认当前工作区而重跑测试，记录真实命令与输出；测试生成的缓存不得清理，且不得因测试结果而修改模型或阈值。

无论测试是否重跑，都不得访问 test split、启动训练、写入正式数据库或项目上传目录。

## 4. 必须交付的文件

在 `reports/u6_4_git_freeze_review/` 新建：

1. `acceptance_report.md`：总体结论、当前状态与基线差异、风险和人工决策点。
2. `file_by_file_review.csv`：每个路径一行，至少包含 `path`、`git_status`、`tracked`、`change_summary`、`task_group`、`runtime_required`、`mixed_change`、`commit_recommendation`、`reason`。
3. `commit_plan.md`：每个建议提交组的顺序、完整文件列表、前置依赖、建议 commit message，以及未来可复制的 PowerShell 命令（仅文本，禁止执行）。
4. `do_not_commit.md`：当前明确建议排除的文件/目录类型与理由，尤其是权重、报告、截图、CSV、缓存、临时 runtime 和数据文件。
5. `working_tree_before.txt` 与 `working_tree_after.txt`：只读状态快照。创建本轮报告会增加新的未跟踪报告目录，需在报告里单独说明，不得把它误记为外部变化。

如果已有同名报告，不得覆盖；应创建带时间或版本后缀的新文件，并在总报告里说明。

## 6. 完成后的停止条件

最终回复只需给出报告目录、当前状态是否与 U6.3 一致、主要混合改动风险、建议提交组概览，以及明确说明 Git 写操作为 0 次。用户审核并明确批准后，才进入单独的 U6.4 执行阶段。
