## 二、方案 B1 的固定口径

### 2.1 四类候选组

候选组必须使用当前 `class_names.json` 中已有的 canonical label：

- `american_pit_bull_terrier` — 美国比特斗牛梗（APBT）
- `american_staffordshire_terrier` — 美国斯塔福郡梗（AmStaff）
- `staffordshire_bull_terrier` — 斯塔福郡斗牛梗（SBT）
- `american_bulldog` — 美国斗牛犬

不能因为候选组扩展而修改 136 类标签目录、合并训练类别、重命名类别或改动任何图片标签。

### 2.2 阈值固定，不重新调参

完全沿用 U5.1 B1 阈值：

- 候选组总概率质量：`group_mass >= 0.30`
- 候选组组内分差：`group_margin <= 0.40`
- 仅当模型原始 Top-1 属于以上四类时，才允许触发。

`group_mass` 为完整 Softmax 概率向量中四类概率之和；`group_margin` 为四类中最高概率减去第二高概率，使用原始概率计算。必须使用完整 136 维概率，不可只用 Top-K；禁止把不在 Top-K 的候选当作 0。

不要为了增加触发率放宽阈值，也不要读取 test split 调整任何规则。

### 2.3 原始模型结果必须原样保留

- 不改 `ml/predict.py` 的原始预测排序、原始 Softmax 概率、Top-K 或 Top-1。
- 不把候选组组内得分伪装成整体置信度、真实概率或准确率。
- 候选组内得分按 `p_i / group_mass * 100` 计算，名称必须明确标注为“候选组内相对得分”。
- 继续在界面上分别呈现“模型预测”和“你选择的品种”；用户选择不得覆盖模型预测。
- 继续保留说明：候选提示不代表已确认犬只的登记品种，单张图片可能不足以可靠区分。
- 用户选择仍仅保存在组件本地状态；本任务不新增 API 写入，不把用户选择写入 SQLite，不更改历史记录 schema。

## 三、实现要求

### 3.1 修改后端候选策略

1. 将 `backend/app/services/candidate_group.py` 中 `CANDIDATE_GROUP` 扩展为上述四类。
2. 使用 U5 已修复的完整 `probabilities` 参数计算候选质量和组内得分。保持对既有调用的向后兼容；若未提供完整概率，按现有实现约定退回原路径，不得因 V1.1 的 37 类缺少部分标签而崩溃。
3. APBT 纳入候选组后：
   - Top-1 为 APBT 且满足阈值时，可以触发候选组；
   - Top-1 不属于四类时仍不触发；
   - 触发时返回四个候选，并且原始 Top-1 与 `predictions[0]` 一致。
4. 为本次四类策略设置清晰可追溯的 `threshold_version`。先检查已有版本命名规范；可以采用类似 `val-2026-10-19-four-breed-b1` 的版本标识，但应遵守项目现有格式。报告必须记录阈值及其来源为 U5.1 validation-only 离线评估。
5. 保持 `CATDOG_CANDIDATE_GROUP_ENABLED` 默认为关闭；不得改动 `weights_path` 默认值。
6. 路由异常兜底继续有效。候选组计算出错时，不得影响原始预测响应。

### 3.2 修改前端展示

1. 在 `frontend/src/utils/breedNames.js` 中补齐 APBT 的中文候选名称；避免破坏现有 37 类映射语义以及既有 breed-name 测试。
2. `PredictionResult.vue` 在后端响应 `candidate_group.triggered === true` 时，显示四个候选类别、组内相对得分和说明文字。
3. 不重排或替换原有 Top-K/模型首选区域；用户选择单独展示，并说明模型首选未被替换。
4. 未触发或功能关闭时，页面保持原有行为，不显示候选区。
5. 不增加“其他三类置信度被人为提高/压低”的处理；分数必须完全来源于完整 Softmax 的组内归一化。
6. 提示文案不得暗示四类中必然存在正确答案，也不得声称用户选择已经得到模型或血统信息验证。
