## A. 任务 1：Git 同步与交付核查（不另做独立任务书）

这是一个短步骤，直接在本任务开头执行，不扩展成单独的 Git 审计项目。

### A1. 只读核查

在项目根目录 `E:\CatDogBreedNet` 执行：

```powershell
git rev-parse HEAD
git branch --show-current
git status --short
git diff --cached --name-status
git diff --name-status
git log -3 --oneline
git ls-remote origin refs/heads/master
```

已知 U6.6 报告中的本地 HEAD 是 `2e83c5f`，`origin/master` 当时落后 3 个提交。必须以本次 `git ls-remote` 的成功返回 SHA 判断远端实际状态，不能只依赖本地 tracking ref。

### A2. 同步规则

1. 若工作区出现未解释的已跟踪修改或暂存内容，先停下并报告，不得覆盖或清理。
2. 检查本地领先远端的 3 个提交是否为预期提交，确认提交内容不含权重、数据库、上传文件、缓存、密钥或机器专属绝对路径。
3. 如果远端分支仍是本地 HEAD 的祖先，且提交审查通过，则执行普通快进推送：
   ```powershell
   git push origin HEAD:master
   ```
   仅在此条件下允许 push；若远端已有本地没有的提交、远端 SHA 异常、网络状态不明确或分支关系不满足快进，立即停止，不执行 force push，不擅自 fetch/pull/rebase。
4. 推送后再次执行：
   ```powershell
   git rev-parse HEAD
   git ls-remote origin refs/heads/master
   git status --short
   ```
   只有远端 SHA 与本地 HEAD 完全一致，才能报告同步完成。
5. 若网络失败，不把失败解释为同步成功；保留首次成功证据或标记“待重试”，不得进行破坏性操作。

Git 核查完成后继续下面的产品改进任务，不为此另生成独立报告目录或独立 Markdown 任务书。

## C. 任务 3：让当前 exp06 的 collie-pair 真正可用（不回退）

### C1. 问题定义

U6.6 证据显示：

- 31 张 `collie` / `border_collie` validation 图中，collie-pair 触发 0 张。
- 全量 2079 张 validation 图中，collie-pair 触发 0 张。
- 原阈值 `COLLIE_PAIR_MARGIN_THRESHOLD=0.30`。
- 旧 V2.1 的触发样本在 exp06 下 margin 变为 0.4076、0.5794、0.3303，均高于 0.30。
- 用户要求：**不回退到 V2.1；直接完善 exp06 下的 collie-pair。**

### C2. 先做定向诊断，禁止盲目调阈值

1. 阅读 `candidate_group.py`、相关 config、测试、U6.6 `raw_eval/` 中 collie/border_collie 预测记录，以及 U6.3/U6.5/U6.6 报告。
2. 用当前 exp06、256 分辨率，在 validation 上重算 collie-pair 的：
   - 31 张目标类图片的原始 Top-1、Top-2、完整 Softmax 概率、pair mass、pair 内归一化 margin；
   - 全量 2079 张图中满足候选组前置条件的数量、候选组触发数量；
   - `collie` 和 `border_collie` 各自的正确率、相互错分情况；
   - 旧 V2.1 已知触发样本在 exp06 下的完整记录。
3. 检查当前策略是否要求原始 Top-1 必须属于候选组。若是，区分“margin 阈值过严”与“前置条件导致无法触发”；不要把所有问题都归因于阈值。
4. 先用离线分析比较原阈值与几个有证据支持的候选阈值/判定方案；阈值只能由 validation 数据选取，并在报告中记录选择过程。不要接触 test split。
5. 候选提示必须保留原始 Top-1、Top-K 和整体分数；候选组得分必须明确标注为组内相对得分，不能冒充整体置信度或真实概率。不得强行显示 50/50，也不得声称候选组一定包含正确答案。

### C3. 可接受的实现方向

按诊断证据选择**最小且可解释**的方案，优先顺序如下：

1. **优先考虑基于 pair mass 与 pair 内相对差异的组合判定**：避免只因模型整体更果断、softmax 绝对值变化就使策略永久休眠。需明确两项量的数学定义、阈值来源与适用范围。
2. 若现有候选组逻辑只支持一个 margin 阈值，可在不破坏四类候选组行为的前提下，为 `collie-pair` 增加独立、明确命名的配置参数；不要无意中改变 `four-breed-bully` 的阈值、成员、版本或行为。
3. 可以考虑在候选组内部按两类概率重新归一化，但这只能决定显示得分，不能单独作为“触发条件已经合理”的证据。
4. 不可通过硬编码某个图片文件名、标签、预测结果或验证样本 ID 来触发。
5. 不允许直接设成 0.99 或无条件触发。必须用 validation 结果展示触发覆盖、错误提示风险和代表性样本。
6. 不修改模型权重，不开展新训练，不访问 test split。

### C4. 策略验收要求

- 当前 exp06 默认下，至少应有可解释的真实 validation 案例触发 collie-pair；如果数据证据不支持任何安全可解释的触发规则，必须报告原因和选项，停止修改，不可为了满足“至少触发”而硬凑。
- 在完整 2079 张 validation 上报告触发数与比例；按真实标签报告触发样本中的正确/错误覆盖情况。
- 明确比较原策略和新策略，确认四类组行为未被意外改变（成员、阈值、版本不变；触发结果差异要解释）。
- 为新逻辑增加单元测试与 API/前端契约回归测试，覆盖：触发、非触发、原始 Top-1 不变、Top-K 不变、候选分数和约为 100、组内得分文案正确、总开关关闭时预测完全不变。
- 保留现有“候选组不保证包含正确品种”的提示语。
- 如新阈值是按 validation 选择的，应明确说明这会使 validation 同时承担策略选择作用；不能再把同一 validation 结果描述为独立的无偏泛化估计。
