# U6.6：exp06 候选切换与毕业设计交付准备

## 一、任务目标

依据用户最新决策，重新处理 U6/U6.1 的研究成果：**`exp06` 是研究候选，不得遗忘或仅因未达到此前的边牧专项冻结门槛就淘汰。只要在可比评估中整体强于当前正式模型，就应切换为默认模型；若提升路线艰难，则停止继续训练。**

现有证据显示：
- 当前 V2.1 baseline Macro-F1：`0.803806`
- U6.1 `exp06`（256 分辨率、低学习率、seed42）Macro-F1：`0.814947`
- `exp06` 三个 seed 的 Macro-F1 均值约：`0.8152`
- 相对 baseline，seed42 Macro-F1 高约 `0.011141`（1.11 个百分点）。
- 同时，已有报告记录 `exp06` 有 7 个类别的 F1 下降超过 `0.10`；边牧专项没有达到原冻结标准。该风险必须如实记录，但按用户新规则，**不能再把此前专项门槛当成自动否决条件**。

任务结论倾向：现阶段不再开展新的训练/调参；只做一次精简的权重身份与同口径验证。若以下兼容性、可复现指标检查通过，就将默认权重切换到 `exp06`。原 V2.1 和 V1.1 文件必须保留，以便回退。

## 二、执行边界

1. 项目根目录：`E:\CatDogBreedNet`。
2. 禁止训练新模型、启动新的超参数搜索或增加新的实验轮次。
3. 禁止访问 `data/v2_processed/test`，任何正式对比仅使用既有报告证据或 validation split。
4. 禁止删除、覆盖、移动任何已有权重，尤其不可覆盖：
   - `artifacts/best_model.pth`（V1.1）
   - `artifacts/v2_1_136classes_seed42/best_model.pth`（V2.1）
   - `artifacts/v2_2_border_collie_exp06_resolution256_lowlr_seed42/best_model.pth`（exp06 候选）
5. 正式 `data/app.db` 与 `uploads/` 不得被冒烟验证写入；使用隔离 DB/uploads。

7. 不推送远端。若完成源代码/配置改动并通过验收，只能对实际改动文件做精确路径暂存和提交，禁止 `git add .`；报告提交 SHA 和工作区状态。若本地 Git 状态与 U6.5 记录不符，先停止 Git 写操作并报告。

## 三、阶段 A：最小化候选确认

### A1. 读取既有证据，不重新做整套实验

查看 U6、U6.1 结果中 baseline 与 exp06 的评估报告，确认指标口径、数据划分、预处理及 class mapping 一致。不得仅凭文件名判定 checkpoint 身份。

### A2. 核验 exp06 权重兼容性

只读检查候选 checkpoint：
- 文件存在、大小合理，计算并记录 SHA256；
- 架构是当前服务支持的 ResNet18，输出类别数为 136；
- 分类头输出顺序与 `artifacts/v2_1_136classes_seed42/class_names.json` 完全一致；
- 所需的模型初始化/推理预处理可由现有服务正常使用；
- 识别并记录 checkpoint 中已有的 epoch、seed、训练配置等元数据（如果存在，不得臆造缺失值）。

如类别数量/顺序不一致或权重无法可靠加载，不可强行切换；停止并给出具体阻塞原因。

### A3. 验证指标是否可直接比较

优先复用已有、同口径的 validation 评估证据。只有在指标来源、split 或计算口径无法确认时，才在**validation split**对 baseline 和 exp06 做最小必要复评；不要训练，不碰 test split。

采用用户已明确的决策规则：在同口径 Macro-F1 下 `exp06 > baseline` 且权重兼容，则切换。类别级明显退化是报告中必须呈现的风险，而不是擅自改成额外否决门槛。若复核推翻了已有指标或发现指标不可比，应停止切换并报告证据，不得猜测。

## 四、阶段 B：切换正式默认模型

在阶段 A 通过后：

1. 将 `config.py`（或项目实际承载默认权重路径的唯一配置源）的默认 `weights_path` 指向 `artifacts/v2_2_border_collie_exp06_resolution256_lowlr_seed42/best_model.pth`。
2. `class_names_path` 仅在已证实类别顺序完全一致后继续指向现有 136 类映射；不得复制/重写 class mapping 来掩盖不匹配。
3. 更新服务中必要的版本标识/启动日志，让版本能明确标识为 `exp06`（遵循项目现有机制，不重复造一套版本协议）。
4. 检查 Windows 启动入口是否覆盖默认配置。仅修改确实会覆盖或硬编码旧权重路径的地方，不要为了统一而进行无关重构。
5. 保留原 V2.1 checkpoint 与元数据原样不动；保留全部实验产物和 U6/U6.1 报告。
6. 补充回归测试：默认权重路径解析到 exp06，136 类与 mapping 校验通过，健康检查版本可区分，V2.1 回退路径仍可用。

## 五、阶段 C：验收

由于正式默认模型变更影响推理路径，改动后必须重新运行相关回归测试：

- `pytest tests/ -q`
- `npm test`
- `npm run build`
- 以默认 Windows 启动等价方式启动后端，但将 `CATDOG_DB_PATH` 与 `CATDOG_UPLOAD_DIR` 重定向到新的隔离目录；模型权重路径/类别映射/候选开关不得被测试环境变量覆盖。
- `/api/health` 必须显示模型已加载、136 类、无模型错误，版本标识明确指向 exp06。
- 冒烟至少包含：一张 collie-pair 已知触发样本、一张 four-breed-bully 已知触发样本、一张 beagle 非目标对照。候选提示只能附加信息，不得替换原始 Top-1、Top-K 和原始分数；候选组内相对得分和约为 100%。
- 确认服务关闭后隔离测试端口释放；正式 DB/uploads 仍分别为 142 条/142 个文件，V1.1 与 V2.1 checkpoint 哈希未改变。

任一关键测试失败时，不要为了通过测试而修改候选算法阈值或删减测试。修复最小必要问题并重跑相关测试；不能修复时保留原 V2.1 默认值，说明阻塞项。

## 六、报告与毕业设计交付准备

输出 `reports/u6_6_exp06_switch/`，控制在以下文件，不堆积一次性产物：

1. `acceptance_report.md`：决策理由、修改文件、测试结果、实际模型版本、切换前后权重路径、回退办法、遗留风险。
2. `model_comparison.json`：baseline 与 exp06 的来源、split、指标口径、Macro-F1、三 seed 结果（有证据才填）、类别级变化摘要。
3. `runtime_smoke.json`：health 与三类冒烟样本的输入/输出断言。
4. `protection_summary.json`：V1.1/V2.1/exp06 的 SHA256、class mapping 校验、正式 DB/uploads 状态。

报告必须清楚区分：
- **整体指标比较好**：如果复核仍同口径，说明 exp06 Macro-F1 优于 baseline；
- **不等于所有类别都更好**：明确列出已有 7 类 F1 下降超过 0.10 的事实和小验证集限制；
- **边牧专项**：写为“专项目标未完全达到，但 exp06 的整体 Macro-F1 高于当前 baseline，因此按用户新的整体指标优先规则采纳”；不可宣称边牧专项已达到原冻结目标或所有错误均被解决。

随后整理毕设交付材料：V1.1（37 类）、V2.1（136 类）与 exp06 的关系；数据集与 split；评估方法及指标；两套候选组策略和限制；系统演示流程；切回 V2.1/V1.1 的回退方式；局限性与类别级退化。不要继续新开 U6.x 调参支线。
