# U5.4 候选组同图一致性与前端回归测试任务

## 任务目标

基于 U5.3 页面验收结果，补齐候选组的前端单元回归测试，并用同一张图片验证：在相同模型与相同配置下，结果应稳定一致；只有候选功能开关改变时，候选区才应按设计出现或消失。

本任务是测试与验收完善，不是模型训练，也不是正式系统发布。

## 当前已知事实

- U5.3 报告中的截图 `01_trigger_apbt.png` 与 `05_switch_off.png` 使用同一张 APBT 图片，但开关状态不同。
- 开启候选组时展示四类候选；关闭 `CATDOG_CANDIDATE_GROUP_ENABLED` 时不展示候选区。这是预期行为，不应被误判为同配置下的随机变化。
- 候选功能默认关闭，正式模型仍为 V1.1（37 类）。V2.1（136 类）是独立候选模型，尚未接入正式系统。

## 严格保护要求

1. 不训练任何模型，不运行训练脚本。
2. 不更改任何图片、标签、数据划分、模型权重或类别映射。
3. 不修改正式模型默认权重路径，不开启正式环境的候选开关，不切换 V1.1 / V2.1。
4. API 验收必须使用隔离的临时 SQLite 和临时 uploads；不得接触正式 `data/app.db` 与 `uploads/`。
5. 不访问 test split；如需图片，使用已有 validation 样本，尤其是 U5.3 已使用的：
   `data/v2_processed/val/american_pit_bull_terrier/american_pit_bull_terrier_132.jpg`
6. 不执行 `git add .`、`git reset --hard`、`git clean`、大范围 checkout 或自动 commit；不清理已有未提交改动和报告目录。

## 工作项

### 1. 补齐前端单元回归测试

在 `frontend/tests/` 中为 `PredictionResult.vue` 增加测试，验证：

- 候选组有 4 个候选时，说明文案显示候选数量为 4（接受界面实际使用的数字格式，例如 `4个候选`）。
- 候选列表数量与候选组说明中的数量始终一致，不能硬编码为 3 或 4。
- 候选组缺失、为 `null` 或未触发时，不显示候选区，也不显示“你选择的品种”区。
- 用户选择候选后，模型原始 Top-1、Top-K 和原始分数不变。

尽量采用最小改动，不重构组件，不改变现有中文文案的含义。

### 2. 同一张图片开启状态重复测试

使用 V2.1 checkpoint 和匹配的 136 类 `class_names.json`，通过已有隔离启动器和 API 测试脚本，使用同一张 validation 图片，在候选开关开启的状态下连续请求至少 5 次。

检查并记录：

- 每次 `candidate_group.triggered` 是否相同；
- 四个候选成员及顺序是否一致；
- 原始 Top-1 标签是否一致；
- 原始 Top-1 分数的最大绝对差；
- 四项组内得分是否始终由完整 Softmax 概率归一化得出，且总和约为 100%。

不要要求不同 GPU batch size 下所有浮点分数逐位相同；若存在微小差异，记录误差，并验证该差异是否足以改变阈值判定。不能为了测试通过而修改阈值。

### 3. 同一张图片开关开/关对照

对同一张 validation 图片分别运行：

- 开启 `CATDOG_CANDIDATE_GROUP_ENABLED`；
- 关闭 `CATDOG_CANDIDATE_GROUP_ENABLED`。

预期：

- 开启时，若满足四类 B1 触发条件，API 返回候选组，前端显示四候选；
- 关闭时，API 不返回候选组，前端不显示候选区域；
- 开关只影响候选提示，不应改变模型权重、原始分类排序或正式配置。

在报告中清楚区分“开关有意改变展示结果”与“同开关配置下的非预期不一致”。

### 4. 回归验证与保护核对

实际运行并记录：

- `.venv\Scripts\python.exe -m pytest tests/ -q`
- 在 `frontend` 目录运行 `npm test`
- 在 `frontend` 目录运行 `npm run build`

核对以下保护项前后未变化：

- `artifacts/best_model.pth`（V1.1）及默认权重路径；
- V2.1 候选权重和对应类别映射；
- 所有原始/清洗/处理数据目录；
- 正式 SQLite 与 `uploads/`；
- 候选开关默认值仍为 `False`。

### 5. 输出报告

在新目录 `reports/v2_1_four_breed_consistency_review/` 下生成：

- `consistency_report.md`：测试设置、重复请求结果、同图开/关对照、通过/失败项；
- `same_image_repeated_requests.csv`：每次请求的开关状态、Top-1、原始分数、是否触发、候选得分；
- `protection_snapshot_before.json` 与 `protection_snapshot_after.json`；
- 如出现失败，保存原始响应和复现步骤，不覆盖 U5.3 既有报告。

## 完成标准

- 前端候选数量文案有自动化单测覆盖。
- 同一图片、同一开关与模型配置下，候选是否触发稳定一致；若不一致，明确定位原因，不以放宽容差掩盖逻辑错误。
- 开关开启与关闭的差异符合预期，原始预测不被候选逻辑改写。
- 后端测试、前端测试、前端构建通过。
- 正式模型、数据、数据库、上传记录均未被修改。

完成后生成报告并停止，等待人工审核。不要自动开启正式候选功能，不要切换正式模型，不要开始 V2.2 训练，不要提交 Git。
